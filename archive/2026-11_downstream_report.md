Host: linux x86_64, Python 3.12.3, gcc 13.3.0, meson 1.12.1, ninja 1.13.2.
All commands were run in this throwaway wp11 scratch directory. Nothing was

## 0. Environment and c2py23 versions

Two throwaway Python venvs were created and used blindly (no edits to the
c2py23 source):

    python3 -m venv venv_main && python3 -m venv venv_new

venv_main had c2py23 installed editable ("main", before the safety changes)
and venv_new had c2py23 installed editable ("fable-review", after the changes):

    venv_main/bin/pip install -e ./c2py23_main
    venv_new/bin/pip install -e ./c2py23_new

Both report version 0.5.10 (the branch did not bump the version number, so the
same version string masks different code). They are genuinely different code:

    c2py23_main  @ 469886e58d19de6004d70c6b5a798c1869fcc5ae  (main, detached)
        c2py23/c2py23/generator.py : 2301 lines, no c2py_check_alignment anywhere
    c2py23_new   @ d9657048c6b67b281fc258ca5d75bc54634c05fb  (branch fable-review)
        c2py23/c2py23/generator.py : 2666 lines, defines c2py_check_alignment /
        check_alignment / derived element-type checks in parser.py and generator.py
        and in runtime/c2py_runtime.h

Both venvs also got the tools both projects need, installed the same way:

    venv_main/bin/pip install numpy pytest meson ninja setuptools wheel h5py hdf5plugin scipy
    venv_new/bin/pip install numpy pytest meson ninja setuptools wheel h5py hdf5plugin scipy

(c2ImageD11 needs numpy + pytest + meson + ninja.  bslz4 additionally needs
h5py, hdf5plugin, scipy.  pyFAI, fabio and CUDA were NOT installed; tests that
need them skip.  Neither venv installs ImageD11, so c2ImageD11's equivalence

Each downstream project was copied to a <name>_main and a <name>_new clone so
the two builds stayed separate:

    cp -a c2ImageD11 c2ImageD11_main && cp -a c2ImageD11 c2ImageD11_new
    cp -a bslz4 bslz4_main && cp -a bslz4 bslz4_new

bslz4 keeps its C sources in git submodules (lz4, bitshuffle, kcb, zstd). They
were uninitialised; I ran `git submodule update --init` once in the original
bslz4 clone before copying, so both bslz4_main and bslz4_new carry the
submodule sources.

## 1. c2ImageD11 (meson + ninja, no ctypes)

Build model (from c2ImageD11/AGENTS.md): the interface files under
lib/interface/ are generated from C2PY_BEGIN blocks in lib/functions/*.c / *.cpp
by tools/harvester.py, which also copies the c2py23 runtime headers from the
installed c2py23 package and generates lib/interface/_cImageD11_wrapper.c.
Then meson + ninja build build/libc2ImageD11/_cImageD11.so, which is copied to
the package dir as _cImageD11.so and _cImageD11_<machine>.so.

Commands run for c2ImageD11_main (same shape for _new, with venv_main -> venv_new):

    cd c2ImageD11_main
    ../venv_main/bin/python tools/harvester.py --output-dir lib/interface   # regenerate
    mkdir -p build/libc2ImageD11 && cd build/libc2ImageD11
    PATH=<abs>/venv_main/bin:$PATH meson setup ../../lib                     # configure
    PATH=<abs>/venv_main/bin:$PATH ninja                                     # build
    cp _cImageD11.so ../../c2ImageD11/_cImageD11.so
    cp _cImageD11.so ../../c2ImageD11/_cImageD11_x86_64.so
    cd ../../..
    ../venv_main/bin/python -m pytest tests/ -rA                             # test

Result:

    c2ImageD11_main  : generation OK, build OK, 54 passed, 1 skipped in 0.44s
    c2ImageD11_new   : generation OK, build OK, 54 passed, 1 skipped in 0.44s

The 1 skip is tests/test_equivalence.py (line 15: "ImageD11 not installed").
Everything else passes, identically, for both versions.

## 2. bslz4 (python tools/build_extension.py + setup.py)

Build model (from bslz4/AGENTS.md): the wrapper src/bslz4_to_sparse_wrapper.c
is committed; it is regenerated by tools/regenerate_wrapper.py from the
C2PY_BEGIN block in src/bslz4_to_sparse.c and a c2py23 package.  The runtime is
vendored in c2py_runtime/.  tools/build_extension.py compiles the .so into src/.
For the tests the package is staged with `setup.py build --build-lib=lib` and the
suite is run with BSLZ4_TO_SPARSE_PATH pointing at lib/.

Commands run for bslz4_main (same shape for _new):

    cd bslz4_main
    # 1. replace the vendored runtime with the matching c2py23 runtime
    RT=<abs>/c2py23_main/c2py23/runtime
    for f in c2py_dlsym.c c2py_dlsym.h c2py_pythonh.c c2py_pythonh.h \
             c2py_runtime.c c2py_runtime.h c2py.h \
             c2py_amd64.h c2py_arm64.h c2py_ppc64.h ; do
      cp -f "$RT/$f" c2py_runtime/$f
    done
    # 2. regenerate the wrapper
    ../venv_main/bin/python tools/regenerate_wrapper.py
    # 3. build the extension
    ../venv_main/bin/python tools/build_extension.py
    # 4. stage the package for testing
    rm -rf lib
    ../venv_main/bin/python setup.py build --build-lib=lib
    # 5. run the test suite
    BSLZ4_TO_SPARSE_PATH=$(pwd)/lib ../venv_main/bin/python -m pytest test -q

Result:

    bslz4_main       : generation OK, build OK, 803 passed, 29 skipped in 74.75s
    bslz4_new        : generation OK, build OK, 803 passed, 29 skipped in 74.16s

The 29 skips are the same in both runs (CUDA and pyFAI/fabio-dependent tests
skipped because neither CUDA nor pyFAI/fabio is installed).  The bslz4 build
info embedded in the .so shows the vendored runtime and wrapper were replaced as
intended: for _main the .so reports "git": "v0.0.22.a3-12-g94264db", for _new it
reports "...-dirty" with the list of replaced files
(c2py_runtime/c2py.h, ... c2py_runtime/c2py_runtime.c, src/bslz4_to_sparse_wrapper.c).

## 3. Interfaces that fail to generate with the new c2py23

None.  Both projects generate every interface successfully with c2py23_new.
The harvester (c2ImageD11) and regenerate_wrapper.py (bslz4) both exited 0 and
produced a wrapper.  In particular WP3 (reject arithmetic on .ptr) broke nothing:

## 4. Generation warnings from the new c2py23

None for either project.  The generator's "no derived element-type check"
warning (WP2, unknown pointee types such as struct pointers) fires on stderr;
I captured generator stderr for both projects and found no such line.  This is
consistent with the interface content: c2ImageD11 buffers map to double / float /
int8_t / uint8_t / int16_t / uint16_t / int32_t / uint32_t / int64_t pointers and
bslz4 buffers map to double / float / int32_t / int64_t / uint32_t / uint64_t /
uint8_t pointers -- every pointee is in the fixed table, so no "unknown pointee"
warning is expected.  (No function appears to set check_format: False either, so
no opt-out path was exercised.)

## 5. Tests that pass with main and fail with new

None.  There is no test in either project that passes with c2py23_main and fails
with c2py23_new.  This is the headline result: despite the new derived element-type
(format) checks, the new alignment checks and the new ndim requirements, every
test that ran still passes.  The reason is that both test suites already call the
functions with correctly typed, aligned, correctly-shaped buffers, so the new
implied checks are satisfied.

## 7. Diff summary of generated wrappers, main vs new

### c2ImageD11 -- representative function bgcalc (float32, already had explicit checks)

bgcalc in c2ImageD11 already declares checks: img.format == 'f', img.ndim == 2,
bg.format == 'f', msk.n == img.n, so WP2's derived format check adds nothing new
for it (the function already constrains format).  What the new wrapper changes
for bgcalc:

    main  (lib/interface/_cImageD11_wrapper.c, the only call site):
        bgcalc((const float *)info_img->ptr, (float *)info_bg->ptr,
               (uint8_t *)info_msk->ptr,
               (intptr_t)(info_img->shape[0]), (intptr_t)(info_img->shape[1]),
               ...);
    new:
        if (c2py_check_contiguity(info_img, ...) < 0)
            return NULL;
        if (c2py_check_alignment(info_img) < 0)      <- NEW (WP2 alignment)
            return NULL;
        ...
        bgcalc(..., (intptr_t)(c2py_shape_at(info_img, 0)),
               (intptr_t)(c2py_shape_at(info_img, 1)), ...);   <- NEW (WP1 bounds-safe)

So for bgcalc the added checks are the per-buffer `c2py_check_alignment(...)` call
and the raw `info_img->shape[k]` read replaced by the bounds-safe
`c2py_shape_at(info_img, k)` helper.

For many other c2ImageD11 functions that had NO explicit format check, the new
wrapper also adds a derived element-type term into the dispatch condition, for
example compute_geometry / compute_xlylzl now gate on terms such as:

    (c2py_format_type(info_xlylzl->format) == 'd')

and single-unconditional-overload functions get a function-level "check failed"
block, for example:

    /* derived check: ((pointers.format == 'q' or pointers.format == 'l') and pointers.itemsize == 8) */

    (that specific example is from bslz4, see below).

The new wrapper is also much larger than the main one (17783 -> 19096 lines), mostly
from WP4 (WP4 perf handle table): main emitted `_c2py_perf_reset` that cast the
Python int straight to `c2py_perf_t*`:

    c2py_perf_reset((c2py_perf_t*)(uintptr_t)ptr_val);      // main (unsafe: any int -> pointer)

whereas the new wrapper looks the handle up through a range-checked table:

    perf = _c2py_perf_lookup(ptr_val);                       // new (WP4)
    if (perf == NULL) { PyErr_SetString(PyExc_ValueError, "invalid perf handle"); return NULL; }
    c2py_perf_reset(perf);

and adds the visible `_c2py_perf_table[]` of static counters.

### bslz4 -- representative function note_chunk (int64_t * pointers, no explicit check)

note_chunk takes `const int64_t *pointers` and `const int32_t *lengths`.  In main the
generated wrapper had NO format check on these buffers.  The new wrapper adds a
derived element-type check (WP2):

    new (src/bslz4_to_sparse_wrapper.c):
        /* derived check: ((pointers.format == 'q' or pointers.format == 'l') and pointers.itemsize == 8) */
        if (!((c2py_format_type(info_pointers->format) == 'q' || ... itemsize == 8))) {
            snprintf(_c2py_err, ..., "note_chunk: arg 'pointers' check failed: ...");
            PyErr_SetString(PyExc_ValueError, _c2py_err);
            return NULL;
        }
        /* derived check: ((lengths.format == 'i' or lengths.format == 'l') and lengths.itemsize == 4) */
        ...
    and read_counters gets a similar one for its uint64_t * out:
        /* derived check: ((out.format == 'Q' or out.format == 'L') and out.itemsize == 8) */

Every buffer in the bslz4 wrapper also gains `if (c2py_check_alignment(info_<buf>) < 0)`.
There is no per-function perf table in bslz4 (grep of the new wrapper for
_c2py_perf_table returns 0), so WP4 does not affect bslz4.

Overall wrapper size 3744 (main) -> 3978 (new) lines; the 234 extra lines are the
alignment checks and the derived element-type checks.

## 10. Bottom line

The safety changes in c2py23 (WP1-WP8) are transparent to these two downstream
projects: every interface still generates, every extension still builds, and
every test suite passes with the same summary line under main and under
fable-review.  The new generator does add derived element-type (format) checks,
alignment checks, bounds-safe shape access and (for the timing-enabled c2ImageD11)
the handle-based perf accessors, but no existing call in either project's tests
trips them.  No interface needed an opt-out key (check_format / check_alignment)
and no unknown-pointee-type generation warnings were emitted.
